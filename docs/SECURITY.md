# SECURITY.md

## 1. Threat model

Assume users may:

- Create fake identities.
- Attempt to access another user's messages.
- Guess IDs/URLs.
- Upload malicious or unsupported files.
- Spam groups.
- Report users maliciously.
- Share private media links.

The goal is strong authorization and safe file handling, not enterprise-grade complexity for a 100-user/day MVP.

## 2. Supabase RLS

All user-facing tables should have explicit Row Level Security policies.

Minimum rules:

### Profiles

- Authenticated users can read public profile fields.
- Users can update only their own editable profile fields.
- Username uniqueness is enforced by the database.

### Conversations

- Only conversation members can read conversation data.
- Only authorized users can create/join conversations according to group privacy rules.

### Conversation members

- Members can read membership where appropriate.
- Only owners/moderators can perform management actions.

### Messages

- Only conversation members can read messages.
- Only conversation members can create messages.
- Only the sender can edit a normal message.
- Moderators/admins can perform authorized moderation deletion.

### Reactions

- Only conversation members can react.
- Users can remove/update their own reactions.

### Notifications

- Users can read/update only their own notifications.

### Reports

- Authenticated users can create reports.
- Only authorized moderators/admins can review them.

### Blocks

- A user can create/delete only their own block relationships.

## 3. Google Drive credentials

Never expose:

- Service-account credentials.
- OAuth client secrets.
- Refresh tokens.
- Drive API access tokens.

These belong in server-side secrets.

## 4. Media validation

Do not trust:

- Filename extension.
- Client-supplied MIME type.
- Client-supplied file size.

Validate on the authoritative path (client-side before upload, and server-side before issuing an upload session).

Reject executable/script content and unsupported file formats.

## 5. XSS/content safety

Messages are text, not arbitrary HTML.

Never dangerously render user-supplied HTML.

Sanitize/escape content appropriately.

Be cautious with Markdown/links if Markdown is introduced later.

## 6. Access control for media

A valid Drive file ID alone must never grant application access.

Application authorization must happen before media access.

Because Google Drive requires server credentials and Vercel limits response sizes:
- A short-lived, signed JWT containing the file ID and user authorization is generated by the Next.js app.
- A dedicated Media Proxy Service uses this JWT to securely fetch and stream the private file from Google Drive to the browser.
- The JWT is cryptographically verified to prevent tampering and ID guessing.

## 7. Admin security

Admin/moderator roles must not be editable by ordinary users through client-side requests.

Use server-side controls and protected database functions/policies where required.

## 8. Authentication security

- Use Supabase Auth.
- Never store passwords in the app database.
- Use secure cookies/session handling through the supported SSR pattern.
- Protect sensitive server routes.

## 9. Logging

Log enough information to troubleshoot security events without logging secrets or sensitive message content unnecessarily.

Do not log access tokens, OAuth credentials, or signed media JWTs.

## 10. Abuse handling

No artificial product-level message rate limit is required for V1.

Still protect expensive operations such as media upload initiation, authentication attempts, and admin actions from obvious abuse.

## 11. Unofficial status

The UI should clearly state that the platform is an unofficial student community and is not an official college communication system.
