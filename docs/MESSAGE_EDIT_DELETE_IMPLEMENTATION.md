# Message Edit and Delete Implementation

## Existing Backend Functionality Discovered
During the inspection, we verified that the backend functionality was already fully implemented:
1. **Server Actions:** `editMessage` and `deleteMessage` were already present and functional in `src/app/app/messages/actions.ts`.
2. **Authorization (RLS):** The server actions included safeguards to ensure users could only edit or delete their own messages (by checking `sender_id === authData.user.id`). We assume database RLS mirrors these checks as standard practice.
3. **Soft Delete:** The `deleteMessage` function implements soft deletion by setting the `deleted_at` timestamp, `deleted_by`, and optionally clearing the text `content`.

## Files Changed
- `src/app/app/messages/[id]/ChatView.tsx`: Added an accessible action menu (dropdown) to expose the edit and delete options for the current user's messages.
- No other files required modification since the underlying logic and Realtime handlers were already in place.

## UI Behavior
- **Hover/Visibility:** On desktop, an action menu trigger (vertical dots) is revealed when the user hovers over their message. On mobile, the trigger is always visible (`opacity-100`).
- **Action Menu:** Clicking the trigger toggles a custom popover menu showing "Edit" and "Delete" options.
- **Edit Mode:** Clicking "Edit" replaces the message bubble with an inline text area and "Cancel/Save" buttons.
- **Delete Confirmation:** Clicking "Delete" prompts a native confirmation dialog before calling the delete action.
- **Visual Indicators:** Edited messages display an "(edited)" indicator next to the timestamp. Deleted messages display a placeholder: *"Message deleted"*.

## Authorization Behavior
- The UI conditionally renders the action menu *only* if `isMine` (i.e. `msg.sender_id === currentUserId`) is true.
- The UI completely hides these options for messages sent by others.
- The server actions (`actions.ts`) perform a secondary hard check, verifying that the authenticated user matches the `sender_id` of the modified message.

## Realtime Behavior
- **Propagation:** Realtime changes automatically propagate because the system uses Supabase's `postgres_changes` listener for the `messages` table.
- **Updates:** The `UPDATE` event listener in `ChatView.tsx` natively handles the changes triggered by both edit (`content` and `edited_at` update) and delete (`deleted_at` and `content` update) actions.
- The local UI state is updated optimistically or upon event receipt, keeping multiple browser windows synchronized without generating duplicate messages.
